# Service bindings

Service bindings let an app consume reviewed Terraform outputs without copying
addresses or identifiers into its manifest. They do not transport secret values.

## Environment registry

Create `dependencies.yaml` in the environment path:

```yaml
dependencies:
  main:
    type: rds-postgres
    module: database
  redis:
    type: elasticache-redis
    module: cache
  jobs:
    type: sqs
    module: queues
    key: jobs
```

The registry maps a stable reference to a Terraform module in the same stack.
Supported MVP types are `rds-postgres`, `elasticache-redis`, and `sqs`.

An app can request specific outputs:

```yaml
dependencies:
  database:
    type: rds-postgres
    reference: main
    env:
      DATABASE_HOST: endpoint
      DATABASE_PORT: port
      DATABASE_NAME: db_name
  cache:
    type: elasticache-redis
    reference: redis
    env:
      REDIS_HOST: primary_endpoint_address
  queue:
    type: sqs
    reference: jobs
    env:
      QUEUE_URL: queue_url
```

`cf app render <name> --env <environment>` generates Terraform expressions such
as `module.database.endpoint`, not copied values.

## Cross-stack outputs

For a dependency in another state, make the output handoff explicit:

```yaml
dependencies:
  main:
    type: rds-postgres
    remote_state: infrastructure
    remote_outputs:
      endpoint: database_endpoint
      port: database_port
      db_name: database_name
```

Rendering uses expressions such as
`data.terraform_remote_state.infrastructure.outputs.database_endpoint` and adds
a reminder to configure that data source. Backend credentials and configuration
remain an environment-root concern and are never generated by the binding layer.

## Secrets

Do not request passwords, tokens, or private keys under `env`. Declare intent
under `secrets` instead:

```yaml
dependencies:
  database:
    type: rds-postgres
    reference: main
    secrets:
      DATABASE_PASSWORD: password
```

The renderer emits only a comment requiring an External Secrets, Secrets Manager,
SSM, or existing Kubernetes Secret reference. It never writes plaintext secret
values. The operator must configure the chosen secret provider and its workload
identity permissions separately.
